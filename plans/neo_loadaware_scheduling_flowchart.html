论文抽象步骤 真实代码逻辑 代码特有 heuristic 局限 / 风险点
A. 主循环总览：调度不是孤立算法，而是一次 iteration 的起点
对应 swiftllm/server/engine.py 的 AsyncEngine._main_event_loop(...)

输入状态

系统持续维护 waiting / GPU decode / CPU decode 三类请求状态，并在每轮 iteration 依据当前负载做局部决策。

↓

1) scheduler.get_next_batch()

返回三个结果：

  • batches：本轮要 forward 的 1 个或 2 个 sub-batch
  • cur_swap_out：本轮需要从 GPU → CPU 的请求
  • cur_swap_in：本轮需要从 CPU → GPU 的请求
↓

2) block_manager.prepare(...)

把高层调度决策翻译成 block table mapping、swap 参数、batch block 分配和 cprf 特殊 swap。

↓

3) executor.do_one_iteration(...)

worker 侧根据 len(batches) 选择：

  • 1 batch → sequential mode
  • 2 batches → pipelined mode
↓

4) update_and_free + remove_finished_requests

写回 output token、释放已完成请求的 block、回收 request id，并更新调度器内部队列。

B. Scheduler 状态机：三队列 + 预算 + block 约束
对应 swiftllm/server/scheduler.py

waiting_q

尚未真正进入执行系统的新请求，等待被 admission。

gpu_decoding_q

当前留在 GPU decode 路径上的活跃请求，默认优先继续服务。

cpu_decoding_q

已经被换出或导向 CPU 路径的请求，后续可能 swap back。

↓

ScheduleBudget

同时限制 max_batch_size 与 max_tokens_in_batch。

GPU blocks

限制 GPU 上 decode / prefill 能否继续留驻。

CPU blocks

限制 CPU swap 空间是否足够接收新 offload 请求。

Request IDs

限制 block table 命名空间，避免新请求没有 request_id 可分配。

C. `_get_next_batch_new(...)`：每轮调度主流程
这是论文附录伪代码在真实仓库中的核心落点

Step 1. 先计算当前 GPU decode 集合的资源占用

把 gpu_decoding_q 视为默认保留集合，统计其 GPU block 需求，并从 budget 中先扣掉这些请求占用的 batch/token。

↓

Step 2. 若 budget overspent 或 GPU block 超阈值，则 swap out

从 gpu_decoding_q 尾部弹出 victim，放到 cpu_decoding_q 头部，并记录到 swpout_reqs。

这是一种近似 FCFS：后到请求更容易被抢占，先到请求更稳定。
↓

Heuristic 1. swap-out / swap-in hysteresis

真实代码采用：

swap_out_threshold = num_gpu_blocks swap_in_threshold = round(swap_out_threshold * 0.95)

目的：避免在边界附近频繁来回 swap。

↓

Step 3. 若 GPU 仍有余量，则尝试 swap in

只看 cpu_decoding_q 队首。若 GPU block 和 budget 允许，则把它搬回 gpu_decoding_q。

按队首做 swap-in，继续体现 arrival-order fairness。
↓

Step 4. 试探性接纳 waiting_q 中的新 prefill 请求

  • 检查 intermediate blocks 是否够
  • 检查 CPU blocks 是否够
  • 检查 request IDs 是否够
  • 检查 batch/token budget 是否够
↓

Heuristic 2. prefill admission 的公平性规则

优先把新 prefill 放入 GPU；但一旦更早的请求已被导向 CPU，后面更晚的请求也倾向继续进入 CPU，而不是重新插到 GPU 抢先。

↓

Step 5. 调用 `_decide_mode_and_gen_batch(...)`

把 pref_to_gpu、pref_to_cpu 和剩余 budget 交给模式决策器，决定本轮到底返回 1 个 batch 还是 2 个 sub-batches。

↓

Step 6. 正式提交本轮 admission

  • 从 waiting_q 真正弹出本轮要接纳的请求
  • 为它们分配 request_id
  • 追加到 gpu_decoding_q 或 cpu_decoding_q
D. `_decide_mode_and_gen_batch(...)`：模式选择与双 sub-batch 构造
这里决定 sequential mode 和 pipelined mode 谁更划算

Step 1. 先形成两个候选世界

  • gpu_only_batch：单 batch sequential 候选
  • batches[0], batches[1]：双 sub-batch pipeline 候选

一开始会把所有 prefill 与 GPU decode 先放入 batch 0。

↓

Heuristic 3. 先裁剪 sequential 候选中的 prefill

如果 linear part 过大，就逐步减少 prefill，直到 batch 的 s 下降到 linr_S_threshold 附近。

linr_S_threshold = 128
↓

Step 2. 把 CPU decode 请求拆入两个 sub-batches

遍历 cpu_decoding_q，动态决定每个 cdec 请求加到 batch0 还是 batch1，而不是简单均分。

↓

核心思想：判断 CPU decode 是否能被 GPU 计算隐藏

论文中的 load-aware，不只是“把 CPU 请求塞进第二个 batch”，而是估计重叠是否成立。

↓

`_get_remains(...)` 计算两个 batch 的 CPU capacity 余额

remains[j] = batches[j^1].linr_T + batches[j].pref_T + batches[j].gdec_T - batches[j].cpu_time

直观含义：当 GPU 在推进这些工作时，CPU 是否还有机会把当前 batch 的 cdec 做完。

↓

Heuristic 4. `min_out_cpu_len` 剪枝

如果某个 CPU decode 请求已经因为太重而导致 min(remains) < 0，后面更长的 CPU decode 请求就直接跳过，避免重复尝试无效候选。

↓

Heuristic 5. 若 CPU 太空闲，再裁剪 batch0 的 prefill

继续减少 batch0 prefill，让 pipeline 的 CPU/GPU overlap 更合理，避免结构失衡。

↓
最终决策： 比较 sequential throughput 与 pipelined throughput。 seqential_time = gpu_only_batch.gpu_time * num_layers pipelined_time = (batch0.gpu_time + batch1.gpu_time) * num_layers seqential_rate = |gpu_only_batch| / seqential_time pipelined_rate = (|batch0| + |batch1|) / pipelined_time
若 pipelined_rate 更高，则返回 2 个 sub-batches；否则返回单个 gpu_only_batch。
E. 为什么叫 Load-Aware：性能预测来源
调度器不是拍脑袋，它依赖 profile tables 与插值

`BatchPerfData` 维护本轮 sub-batch 的局部负载

  • x：请求数
  • s：iteration width
  • n_g：GPU decode token 总量
  • x_c：CPU decode 请求数
  • n_c：CPU decode token 总量
↓

由 predictor 估计时间项

  • linr_T
  • pref_T
  • gdec_T
  • cdec_T
  • lnch_T

`TablePerfPredictor`

保存四类 profile tables，并使用一维 / 二维插值估计未测点。

↓

`ModelProfiler.init_profile_tables(...)`

真实构造 test cases，实际跑模型，收集 linear / prefill / GPU decode / CPU decode 的平均时间。

↓

对应论文中的 profile-guided scheduling

不是静态规则，而是“离线 profile + 在线插值 + 每轮 greedy 决策”。

F. BlockManager：把调度决策落成 block 操作
对应 swiftllm/server/block_manager.py

1) conventional swap

若本轮有 cur_swap_out 或 cur_swap_in，则调用 _initiate_swap(...)，获得 source/destination block 映射。

↓

2) 对每个 batch 调用 `set_model_forward_args(...)`

把调度阶段的请求分类，转换成 worker 真正需要的 forward 参数：num_cprfs / num_gprfs / num_gdecs / num_cdecs / sum_pref_toks / seq_block_size 等。

↓

3) 给 GPU / CPU 两侧分配新 blocks

这一步是真正把逻辑 batch 变成底层 block table state。

↓

4) 对 cprf 再做额外 swap

CPU-prefill 请求并不是纯 CPU 路径，还要处理 intermediate cache → CPU 的特殊 swap。

G. Worker 执行分支：1 个 batch 和 2 个 batch 的语义完全不同
对应 swiftllm/worker/model.py 与 swiftllm/worker/layers/transformer_layer.py
Sequential mode（返回 1 个 batch）

`_forward_batches(...)` → `_forward_sequential(...)`

所有 transformer layers 逐层顺序推进，一个 batch 走完整条路径。

↓

适用场景

pipeline 无法带来足够收益，或者当前负载结构下双 batch 会让吞吐下降。

Pipelined mode（返回 2 个 sub-batches）

`_forward_batches(...)` → `_forward_pipeline(...)`

通过 forward_first_stage、forward_double、forward_last_stage 进行 layer-wise 流水。

↓

layer 内部的真实交错

一批做 postproj[i] → preproj[i+1]，另一批做 attention[i]，两批在层之间交替推进。

↓

适用场景

CPU decode 能被 GPU 的 linear/prefill/gdec 工作有效隐藏，且总体吞吐预测更高。

H. Paper vs Code：一致处与偏离处

与论文一致的地方

  • 每轮做 profile-guided greedy scheduling
  • 同时考虑 prefill / GPU decode / CPU decode
  • 显式比较 sequential 与 pipelined 两种候选
  • 重视 CPU/GPU overlap，而不是只看单设备负载

代码额外加入的工程化 heuristic

  • swap_in_threshold = round(swap_out_threshold * 0.95) 防抖
  • linr_S_threshold = 128 限制 linear 过载
  • min_out_cpu_len 剪枝长 CPU decode 候选
  • pref_to_cpu 的 fairness 规则
  • 显式考虑 request-id 和 intermediate blocks
I. 这种调度方式的局限

Heuristic 依赖硬件

阈值与 profile tables 都可能随着 GPU、CPU、模型大小、kernel 实现变化而失效。

局部最优，不是全局最优

它是 per-iteration greedy scheduler，不会显式优化长期 tail latency 或未来 contention。

fairness 只是近似 FCFS

arrival order 受到保护，但资源约束与异构路径会让真实完成顺序偏离严格 FCFS。

overlap 判断是近似模型

_get_remains() 很聪明，但仍无法完全捕捉 stream 同步、PCIe、缓存、launch jitter 等细节。

边界附近可能 oscillation

即便有 hysteresis，某些负载边界仍可能在 sequential 与 pipeline 之间反复切换。

最终 rate 公式偏向 GPU 侧

CPU 影响更多通过 admission heuristic 间接体现，不是严格的联合优化目标。

J. 复现时最该抓住的主线

核心原则

不要把 NEO 理解成“固定地把一部分请求放 CPU”。真正的关键是：每轮都根据当前负载和 profile 结果，动态决定谁留 GPU、谁去 CPU、谁能进入系统、这一轮值不值得 pipeline。

↓

最值得反复读的 4 个函数

  • Scheduler._get_next_batch_new(...)
  • Scheduler._decide_mode_and_gen_batch(...)
  • BlockManager.prepare(...)
  • LlamaModel._forward_batches(...)
